# 外部接続・外部実行ファイルのセキュリティ対策計画

作成日: 2026-10-24（JST）  
対象: obs-delay-stream / Windows / cloudflared / FFmpeg / HTTP・WebSocket受信処理  
状態: 計画書作成済み。対策の実装・検証・実機確認はすべて未実施で、各作業は実行範囲の承認後に行う。

## 1. 目的と進め方

既知の脆弱性への更新対応を可能にし、未認証の外部入力がOBSへ届く機会を減らす。未知の脆弱性が残る場合にも、音声配信・OBS・利用者のファイルへの影響を限定する。

想定利用は、READMEに記載された「最大20人の出演者がGoogle Chromeで音声を受信する」運用とする。出演者を限定する認証を標準案にし、不特定多数への匿名公開は別の運用として扱う。

優先順位は次のとおり。

1. 外部から届く入口を、小さな差分で先に塞ぐ（P2の即効項目）。
2. 実際に利用する依存物を把握し、修正版へ更新できるようにする。
3. 受信量・接続数・接続コードの制限を仕上げる。
4. Cloudflare側の認証で、未認証アクセスをOBSへ転送しない。
5. FFmpegなどの子プロセスを制限し、終了漏れを防ぐ。
6. 公開サーバーをOBSから分離する。これは別段階として設計する。

P2の即効項目は数十行規模の変更で外部入力の到達範囲を直接狭められるため、取得・検証の仕組みを作るP1より先に出す。P0の現物把握はコード変更と並行して進める。

## 3. 守る境界

現在の主な経路は次のとおり。

```text
インターネット上の接続者
    → Cloudflare → cloudflared → OBS内のHTTP/WebSocketサーバー

RTSP送信元
    → FFmpeg子プロセス → PCMパイプ → OBS内の計測処理

依存物の配布元
    → ダウンロード／展開 → ローカルexe → プロセス起動
```

| 脅威 | 初期対策 | 残る限界 |
|---|---|---|
| 外部からの不正なHTTP・WebSocket入力 | 入口認証、入力上限、厳密な構文検査 | 認証済み利用者からの攻撃や解析器の未知の欠陥 |
| URL・接続コードの流出 | 暗号学的乱数、失効、ログ抑制、入口認証 | 正規利用者によるURL転送やメールアカウント侵害 |
| 大量接続・大きな入力によるOBS停止 | 接続・受信・待ち行列の上限、タイムアウト | 回線帯域の枯渇、上流サービスの停止 |
| 改変された取得物・古いexeの実行 | 承認版のハッシュ固定、既知危険版の拒否、更新運用 | 配布元と承認手続きの双方が侵害された場合 |
| 不正RTSPによるFFmpeg侵害 | 接続先・形式の制限、更新、子プロセス制限 | 通常ユーザーの権限を持つ子プロセスの侵害 |

cloudflaredの転送先がlocalhostでも、トンネル経由のアクセスは到達する。ループバック限定はLANなどからの直接接続を防ぐ対策であり、トンネルの認証を代替しない。

Cloudflare WAFはWebSocketの初期HTTP要求を検査するが、接続成立後のメッセージは継続検査しない。サーバー側の入力検証は別途必要。[Cloudflare公式仕様](https://developers.cloudflare.com/network/websockets/)

| 段階 | 優先度 | 成果物 | 着手条件・依存 |

| P1 更新管理 | 高 | 検証付き取得、実ファイルの状態表示、安全な更新 | P0で取得元・承認版を確定 |

| P4 子プロセスの制限 | 中 | FFmpeg入力制限、終了保証、権限の評価 | P1。P2・P3と並行可能 |

## 5. 段階別の実施内容

### P0: 現物把握と暫定運用

1. プラグインが選択しているAuto／PATH／手動指定を確認し、実際に解決されるexeの絶対パスを記録する。PATH上の別のexeだけを確認して完了にしない。
2. cloudflared・FFmpegの版、SHA-256、入手元、確認日を記録する。署名がある場合は発行者と有効性も記録する。不審なexeをバージョン表示のために起動しない。
3. OBS、WebSocket++、Asio、libopus、配布するreceiver依存物の版／コミットを一覧化する。OBS同梱ライブラリと、このプラグインが直接管理するexeを区別する。
4. 更新確認が済むまで外部トンネルを停止する暫定運用と、利用時だけ公開する運用を案内する。実際の停止・更新は利用者の作業時間に合わせる。
5. cloudflaredの修正版を選定する。2026-10-20のCloudflare告知は証明書問題への対応として2026.10.2への更新を案内している。計画作成時に確認した最新版は2026.10.3。実施日にも告知とリリースを再確認する。[公式告知](https://blog.cloudflare.com/emudhra-certificate-compromise/)・[2026.10.3](https://github.com/cloudflare/cloudflared/releases/tag/2026.10.3)
6. FFmpegはバージョン番号だけで安全と判定せず、採用する配布ビルドのソースコミット・構成と修正情報を突き合わせる。採用版とハッシュはこの段階で確定する。[FFmpeg Security](https://ffmpeg.org/security.html)

完了条件: 使用中の実体と承認する更新先が特定され、変更前後の記録と停止／復旧手順が揃う。

### P1: 外部実行ファイルの取得・更新管理

**取得方針**

- 初期実装は、リポジトリで管理する小さな承認一覧に「製品・版／コミット・配布URL・SHA-256・許可する起動能力」を記録する。汎用のパッケージ管理システムは作らない。
- cloudflaredの`latest`、FFmpegの`master-latest`を直接実行物として採用する処理を置き換える。FFmpegはexe以外の同梱DLLも含めた配布単位を管理する。
- 取得は専用の一時領域へ行い、ハッシュ検証後に展開する。展開先外への書き込み、既存ファイルの上書き、不必要な再帰探索によるexe選択を避け、採用する実行パスを固定する。
- 承認一覧そのものを信頼の基点にする。exeと同じ取得先から毎回ダウンロードしたハッシュを無条件に信用する構成にはしない。ハッシュ一致は配布元の健全性を保証しないため、更新元の告知も確認する。
- BtbNの日付付きビルドは保持期間が保証されていないため、承認したURLが後で取得できなくなる前提で設計する。承認版をこのリポジトリのGitHub Releaseへ転載するか、取得不能時は新しい版を承認し直すかをP0で決める。取得できない場合も別のビルドや`latest`へ自動で切り替えない。

**更新・起動方針**

- UIには解決後のパス、版、検証状態、更新候補を表示する。Autoの既存ファイルも初回移行時と起動前に検証する。
- 実行中のexeを上書きしない。検証済みの別バージョン用ディレクトリへ配置し、停止後に参照先を切り替える。失敗時は既存配置を破壊しない。
- 起動経路は「通常起動」「起動して次へ」「自動取得」「手動取得」で共通の検証を通す。
- 既知の危険版は対象機能の起動を拒否する。未知の版を「安全」と表示しない。外部ツールが使えなくても、無関係なOBSの音声処理は継続させる。
- PATH／手動指定を勝手に上書きしない。承認一覧外のexeは「外部管理・未検証」と表示し、管理者が信頼する取得元を確認する運用を明記する。Autoモードから未検証exeへの暗黙の切替は行わない。
- ネットワーク障害時は、既知危険版でない検証済み配置だけを使用可能とする。検証失敗や認証機能の不足を理由に、安全性の低い起動へ自動で切り替えない。
- 初期段階の新しい承認一覧はプラグイン更新で配布する。上流の版確認は手動操作とリリース前確認を基本とし、任意のリモート一覧をそのまま信頼する自動更新は後続検討にする。

Windows版cloudflaredは自身では自動更新しないため、この更新経路と運用を明示する。[公式説明](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/downloads/)

完了条件: 改変・不完全なダウンロードを実行しない。承認版への更新と安全な復旧が可能。UI表示と実際に起動した実体が一致する。

### P2: 待受・認可・入力上限

**即効項目（初回のコード変更）**

以下は既存構造のまま適用でき、外部から届く入口を直接狭める。P1の承認一覧より先に、独立した差分として出す。

1. 待受をループバック（`listen("127.0.0.1", port)`相当）に限定し、LAN直接配信（IP自動設定・IP手動設定・ダイレクトIPのURL共有）を撤去する。cloudflaredの転送先も同時に`127.0.0.1:<port>`へ揃える。`localhost`のままでは`::1`へ解決されて接続できない可能性がある。
2. `set_max_message_size`・`set_max_http_body_size`で受信上限を設定する。
3. `set_validate_handler`でUpgrade承認前に配信ID・チャンネルコード・Origin／Hostを照合する。
4. `on_message()`から全体のビットレート・サンプルレート変更を削除する。配布receiverは送っていないため互換性への影響はない。
5. コード生成を`BCryptGenRandom`へ切り替える。

コード長の変更と旧コードの移行は共有URLの再配布を伴うため、即効項目とは分けて「接続コードと認可」の方針で進める。

**待受と起動**

- 待受は常にループバックとし、外部の受信者はトンネル経由だけで受け付ける。cloudflaredの転送先も`127.0.0.1:<port>`に統一する。IPv4／IPv6の両方で意図しない待受がないことを確認する。
- LAN直接配信は撤去する。平文のHTTP/WebSocketでチャンネルコードが同じネットワーク上に流れ、ファイアウォール開放やルーターのポート開放をユーザーの判断に委ねるため。撤去により、Cloudflareが使えない環境では外部共有の代替経路がなくなる。
- 旧設定の`host_ip_manual`（IP手動設定）と`auto_ip_info`は読込時に削除する。読み込み時の検証は未知のキーを無視するため、旧版で保存・書き出しした設定もそのまま読める。LANで直接配信していた利用者は、更新後はトンネルの起動が必要になることをリリースノートで案内する。

**接続コードと認可**

- Windowsの`BCryptGenRandom`で16 bytesの乱数を生成し、32文字の16進表現をチャンネルコードにする。乱数生成失敗時は発行を中止する。
- `generate_stream_id()`の全呼び出し元を確認し、配信IDとチャンネルコードの用途を分ける。IDを秘密の認証情報として二重に頼らず、チャンネルコードに128 bitの乱数を確保する。
- WebSocketのUpgradeを承認する段階へ照合を移す。空の配信ID、不正なコード、無効チャンネルを拒否する。`sanitize_id()`で入力を別の有効コードへ変換せず、長さ・文字種・構造の不一致を拒否する。
- Upgrade時に`Origin`と`Host`を検査する。即効項目では`Origin`が`Host`と同一オリジンであることを求め、別サイトのページからのWebSocket接続を拒否する。ループバック待受へのDNS rebindingを防ぐには`Host`を共有URLのホスト（Quick Tunnel、外部管理の公開URL、ループバック）に限る許可リストが必要で、公開URLを扱うP3で追加する。
- 各制御メッセージ処理でも認可済み接続であることを確認する。受信者のPCMフォールバックは保ち、全体のビットレート・サンプルレートを受信者から変更する経路は閉じる。
- 制御メッセージは部分文字列検索をやめ、JSONとして解析する。型・既知キー・値の範囲を検査し、不一致は破棄する。
- `/config`は受信ページの表示に必要な範囲だけを返す。現在の有効チャンネル数の開示を受容するか、認可済み要求に限定するかを決める。Access導入後も直接接続経路で露出しないことを確認する。
- 再発行時は対象チャンネルの旧コードを即失効させ、既存接続も閉じる。次回起動まで旧コードが有効な状態を残さない。
- 共有ページの既存のURLフラグメント形式を維持し、`Referrer-Policy: no-referrer`を追加する。WebSocketパスと`/memo`クエリにはコードが渡るため、サーバー／トンネルのログで秘匿する。フラグメントだけで漏えいが解決したと扱わない。

**入力制限の初期候補**

以下は採用候補値であり、既存20人運用の受入確認前には確定値としない。低い上限を設ける対象は主にクライアントからの制御入力で、サーバーが送る音声サイズとは区別する。

| 項目 | 初期候補 | 超過時の動作 |
|---|---|---|
| WebSocket受信メッセージ | 4 KiB、フラグメント再構成後にも適用 | 当該接続を閉じる |
| HTTP本文 | 1 KiB上限。通常の配信用GET／HEADには本文不要 | 本文を蓄積し続けず拒否 |
| URL・クエリ | 2 KiB | 拒否 |
| HTTPヘッダー全体 | 既定の16,000 bytesを維持（コンパイル時定数のため設定では変えない）。AccessのCookieサイズとの互換性を確認 | 解析器側で拒否 |
| 認証済みWebSocket | 有効チャンネルごとに1接続、最大20 | 既存の再接続仕様と整合させる |
| 未認証・HTTP接続を含む総接続 | 64接続、未完了ハンドシェイクは16接続 | 新規接続を拒否。確立済み音声接続を巻き込まない |
| ハンドシェイク時間 | 既定の5秒を維持。延長しない | 当該接続を閉じる |
| 制御入力頻度 | 接続ごとに20件/秒、短時間バースト40件 | 違反接続を制限／切断 |
| 音声送信待ち | 接続ごとに2秒相当を上限候補 | 遅い接続を切断し、OBS音声スレッドを待たせない |

総接続上限には、HTTPの短期接続、ハンドシェイク失敗、切断処理中の接続も含め、失敗・closeの各経路でカウンタを戻す。上限をハンドラーで調べるだけでは解析時のメモリ増大を防げないため、WebSocket++の設定・accept処理への適用箇所まで確認する。

静的ファイルは配布するreceiverアセットだけを提供する。既存の`is_safe_rel_path()`は`..`・`\`・`:`を拒否し、パスをURLデコードしないため`%2e`による迂回は成立しない。残る対策は、配信ルート内のreparse point経由で外部ファイルを読ませないことと、読み込むファイルサイズの上限設定。

トンネル越しではTCP接続元がlocalhostとなるため、それを利用者別IPとして制限しない。外部由来の転送ヘッダーも無条件に信用しない。接続単位・総量の制限を先に実装し、利用者別制限はCloudflare側の認証と組み合わせる。

完了条件: 不正コードをUpgrade前に拒否できる。失効済み接続が音声を受信できない。上限超過がOBS全体の停止や無制限のメモリ増大につながらず、通常の20人接続・再接続が成立する。

### P3: OBSに届く前の認証

**初期実装: メール認証付きQuick Tunnel**

- 一時的な出演者共有の標準として、許可する個別メールアドレス一覧を設定し、対応するcloudflaredへ`--allowed-mail`を渡す。
- アドレス一覧が空、対応版でない、引数が不正、認証付き起動が失敗した場合は公開を開始しない。認証なしでの再試行は行わない。
- 公式ドキュメントは`--allowed-mail`の最低バージョンを示していない。対応可否は承認一覧に版ごとに記録し、未記録の外部管理exeでは`tunnel --help`の出力に`--allowed-mail`があることを確認できた場合だけ起動する。
- 設定は専用フィールドとして保持し、任意の追加コマンドラインを入力させない。アドレスの改行・引用符などを検査し、Windowsの引数規則に従って渡す。
- メール一覧変更時は既存のQuick Tunnelを停止して再作成する。URL変更と再共有が必要なことを表示する。
- 旧来の認証なし公開を残す場合は、明示選択する互換モードとし、初期値やエラー時のフォールバックにはしない。

Cloudflareの現行仕様にはメール認証付きQuick Tunnelがあるが、対話的なブラウザー利用が必要。Quick Tunnel自体は開発・テスト向けであり、本番運用の可用性保証として扱わない。同時処理リクエストは1本あたり200件までで、超過分はHTTP 429になる。WebSocketへの言及はないため、採用exeの対応状況、認証後のWebSocket接続、URLフラグメントの維持は受入確認に含める。[公式仕様](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/)

**継続的な本番運用: 管理対象Tunnel + Cloudflare Access**

- 管理対象Tunnelを運用者が管理し、Accessで許可した出演者だけを通す。ドメイン・アカウント・利用可能な契約条件は運用開始前に確認する。
- 初期実装ではTunnel作成APIやアカウント管理をプラグインへ組み込まない。外部管理されたHTTPSの公開ベースURLを設定できるようにし、共有URLをそこから生成する。
- 対象ホストの受信ページ・アセット・`/config`・`/memo`・WebSocketパス全体を保護する。別ホストや直接接続で認証を迂回できないようにする。
- 外部管理のTunnelを使う間は、プラグインのQuick Tunnelを同時に開かない。運用者がAccessとトンネル側の検証設定を確認する。URLの入力だけで「認証済み」と表示しない。
- プラグインが管理しないサービスは停止ボタンの対象外であることを明示する。公開停止手順は、OBS側サーバー停止と外部Tunnel停止の両方を記載する。
- Accessのログイン有効期限と、既に成立しているWebSocketの切断は別に扱う。即時失効時はコード再発行と接続切断を併用する。

Accessは利用者の認証・許可を担い、チャンネルコードは各受信先の権限を担う。メール認証だけで特定のチャンネルまで自動的に紐付くとは扱わない。[Cloudflareの構成説明](https://developers.cloudflare.com/reference-architecture/design-guides/designing-ztna-access-policies/)

完了条件: 未許可ユーザーのHTTP／WebSocket要求がOBSへ転送されない。許可したChrome利用者は認証後に音声を受信できる。認証障害時に匿名公開へ切り替わらない。

### P4: FFmpegと子プロセスの制限

- RTSP URLを構造として検査し、schemeをrtsp・rtsps・rtsptに限定する。任意ファイル・別プロトコルを同じ入力欄から読ませない。URLはOBSの配信URLからの自動導出か運用者の手動入力であり、引数のエスケープも既存処理で行っているため、送信元ホストの許可リストは設けない。
- `-f rtsp`などによる入力形式固定と`protocol_whitelist`を採用ビルドで確認する。RTSPはdemuxer、TCP/TLSなどは下位プロトコルであるため、名前の羅列を推測で固定しない。入力とPCMパイプ出力のオプション範囲を分ける。[FFmpegの仕様](https://ffmpeg.org/ffmpeg-protocols.html)
- 認証情報を含むRTSP URL、stderr、コマンドラインを公開ログへそのまま出さない。子プロセスが認証情報を受け取る点は残るため、管理している送信元専用の資格情報を使う。
- `STARTUPINFOEX`のハンドル継承リストなどで必要なパイプ／ログ以外を継承させない。依存物専用の作業ディレクトリを使い、DLL探索やPATHによる想定外の実行物選択を減らす。
- プラグインが起動した子プロセスをJob Objectへ登録し、OBS異常終了時にも残存しないようにする。登録前に走り始めない起動順序を設計する。外部管理サービスや利用者が起動した同名exeは対象にしない。
- 既存の計測タイムアウトを維持し、stderrの保持量、メモリ、子プロセス数も制限する。メモリ上限は採用ビルドの正常計測に必要な量を確認して決め、音切れを招くCPU制限を推測で入れない。
- OBSの通常ユーザー実行を基本とする。Job Objectは終了・資源制限であってファイルアクセスを隔離するサンドボックスではない。AppContainer／制限付きトークンは別の権限評価と互換性確認を経て導入する。[Microsoft Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)・[AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation)

完了条件: 不許可入力をFFmpegへ渡さず、停止・タイムアウト・OBS異常終了で管理対象の子プロセスが残らない。正常なRTSP E2E計測は継続できる。通常ユーザー権限での侵害リスクが残ることを明記する。

### P5: 公開サーバーをOBSから分離する設計

P1〜P4では、認証済み接続から届くHTTP／WebSocketをOBS内で解析する構造が残る。これが受容できない場合に着手する。

- HTTP／WebSocketを低権限の専用プロセスへ移す。cloudflaredだけを別プロセス・別コンテナへ移して完了としない。
- OBSとの通信はACLで制限したIPCにし、音声データと必要最小限の制御だけを流す。長さ・型・状態・権限をOBS側でも検査し、任意の設定変更やコマンド実行を許さない。
- 外部プロセスが停止・侵害されても、OBSの音声スレッドがブロックせず、権限の強い操作を代行しない設計にする。
- サンドボックスのネットワーク許可、DLL読込、音声配送の遅延、配布・更新の複雑化を小さな試作で評価する。

成果物は別の設計書と試作評価。性能・互換性・権限分離の成立を確認するまでは、初回リリースへ含めない。

## 7. 既存設定の移行と復旧

| 変更 | 移行方針 | 失敗時の扱い |
|---|---|---|
| 既存exe | 検証してから管理済み配置へ移行。外部管理パスを勝手に置換しない | 旧版が検証済みかつ既知危険版でない場合だけ復旧候補にする |
| 8文字コード | 旧値を無言で変更しない。公開再開前に「コード更新とURL再共有」を明示して移行 | 移行前設定を退避するが、失効させたコードは復活させない |
| 待受範囲 | ループバックに限定し、旧設定のIP手動設定は読込時に削除 | LAN直接配信へ戻す設定は設けない。外部共有はトンネルを使う |
| メール認証 | 許可リストと対応exeを揃えてから起動 | 失敗時は公開停止状態を維持 |
| 管理対象Tunnel | 運用者が設定を管理し、プラグインには公開URLだけを登録 | Quick Tunnelへ自動切替しない |
| サーバー変更 | 音声設定・計測結果を保持して対象機能を停止 | 一般のOBS音声処理を止めず、原因と復旧手順を表示 |

停止の順序は「外部公開停止 → クライアント切断／サーバー停止 → 必要なら子プロセス停止」。外部管理のTunnelは運用者側でも停止する。設定退避にはコード等が含まれるため、公開のバグ報告へ添付しない。

## 9. 継続運用とインシデント対応

- 保守担当は週1回とリリース前に、cloudflared、FFmpeg、OBS、WebSocket++、Asio、libopus、receiver依存物の公式告知を確認する。担当者・確認日・採否理由を依存物一覧に残す。この計画書による定期実行や通知の設定は行っていない。
- Dependabotの既存対象に含まれないexe・vendored依存物は別途追跡する。スキャン結果は「対象版・到達経路・修正版」を確認し、検出件数だけで判断しない。
- 外部から到達できる重大問題や悪用情報を確認した場合は、まず公開停止または該当機能停止を判断し、修正版の採用を優先する。停止を避けるために旧版へ固定し続けない。
- ログは版・エラー分類・拒否件数・更新結果を中心に残す。受信本文、接続コード、URL内の資格情報、メール一覧を常時記録しない。認証失敗ログにも件数上限を設ける。
- 侵害が疑われる場合は公開を止め、ログ・使用版・時刻を保存する。必要に応じて配信コード、RTSP資格情報、Cloudflareの資格情報を更新する。侵害が疑われるPCからの秘密情報再発行は避け、信頼できる環境で行う。
- コード流出だけの場合とexe／OBSプロセスの侵害では対応範囲が異なる。後者はプラグイン更新だけで復旧完了にせず、ホストと資格情報の調査を含める。
