# 実機確認の手順

`docs/security-hardening-plan.md` の検証計画（9章）のうち、OBS・Chrome・トンネル・RTSP 計測で確かめる項目の手順。自己チェック（`stream-router-utils-check`、`plugin-utils-check`）で判定を確かめた項目も、実際の接続で確認する。

## 準備

- 試験用の OBS プロファイルとシーンコレクションを使う。負荷をかける確認は、公開中のトンネルや本番配信で行わない。
- OBS のログは「ヘルプ → ログファイル → 現在のログを表示」で開き、`[obs-delay-stream]` で検索する。
- プロセスの確認には、タスクマネージャーの「詳細」タブを使う。
- 受信ページでの操作には、Chrome の開発者ツール（F12）のコンソールを使う。受信ページが使っている WebSocket はコンソールから参照できないため、確認用の WebSocket を自分で開く（各項目に記載）。チャンネルごとに接続は1つなので、確認用の接続を開くと、同じチャンネルの受信ページは置き換えられて切断される。

結果は項目ごとに「合格・不合格・未実施」と、気づいた点を記録する。

## 1. 外部実行ファイル（V01・V02）

| 手順 | 期待する結果 |
|---|---|
| cloudflared のパスを「自動」にし、`%LOCALAPPDATA%\obs-delay-stream\bin\cloudflared\` が無い状態でトンネルを起動する | `...\bin\cloudflared\2026.10.3\cloudflared.exe` が作られ、トンネルが起動する。ログに `cloudflared auto-download: 2026.10.3` が出る |
| トンネルを停止して、もう一度起動する | ダウンロードせずに起動する |
| RTSP 計測を「自動」の ffmpeg で初めて実行する | `...\bin\ffmpeg\ffmpeg-n9.0.2-17-g2a571b6068-win64-lgpl-9.0\bin\ffmpeg.exe` だけが作られる（ffplay・ffprobe は無い）。計測が始まる |
| 停止中に、配置済みの `cloudflared.exe` を別の exe（例: `C:\Windows\System32\where.exe` のコピー）で上書きしてからトンネルを起動する | 承認版を取得し直して起動する。上書きした exe は起動しない |
| ネットワークを切った状態で、配置済みの承認版を消してからトンネルを起動する | エラーを表示して起動しない |
| パスを「手動指定」にして任意の cloudflared.exe を指定する | パス欄の下に「PATHや手動で指定した cloudflared.exe は検証しません」と表示され、起動できる |
| 以前の版で自動取得した `%LOCALAPPDATA%\obs-delay-stream\bin\cloudflared.exe` を手動指定した設定を読み込む | 読込時にパスが「自動」へ戻る |

## 2. 受信サーバー（V03〜V07）

| 手順 | 期待する結果 |
|---|---|
| WebSocket サーバーを起動し、コマンドプロンプトで `netstat -ano \| findstr :19000` を実行する | `127.0.0.1:19000` の LISTENING だけがある（`0.0.0.0` や `[::]` は無い） |
| 同じ LAN の別の PC から `http://<このPCのIP>:19000/` を開く | 接続できない |
| 出演者用 URL のコードを1文字変えて開く | 「コードが見つかりません」と表示され、音声は届かない |
| 出演者用 URL の配信 ID を1文字変えて開く | 「配信IDが一致しません」と表示される |
| 受信ページとは別のサイト（例: 任意の https のページ）のコンソールで `new WebSocket('wss://<トンネルのホスト>/<配信ID>/<コード>')` を実行する | 接続できない（Origin 検査で拒否） |
| 出演者を接続したまま、出演者名タブでそのチャンネルを削除する | その出演者は切断される。追加し直したチャンネルの新しい URL で接続できる |
| 受信ページのコンソールで、確認用に `w = new WebSocket(location.href.replace(/^http/, 'ws').replace('/#!', ''))` で接続したあと `w.send('x'.repeat(5000))` を実行する | `w` が切断される（close code 1009）。OBS の音声は途切れない |
| 確認用の接続で `w.send('not json')` を実行する | `w` が切断される |
| 確認用の接続で `for (let i = 0; i < 100; i++) w.send('{"type":"pong","seq":1}')` を実行する | `w` が切断される（rate_limited）。ほかの出演者の音声は続く |
| 確認用の接続で `w.send('{"type":"audio_codec","mode":"opus","bitrate_kbps":24}')` を送る | ほかの出演者の音質は変わらない |

## 3. トンネル経由の接続（V10）

最も重要な確認。Origin 検査は、cloudflared が元の Host ヘッダーを転送することを前提にしている。

| 手順 | 期待する結果 |
|---|---|
| トンネルを起動し、URL 共有タブの URL を別のネットワーク（スマートフォンのテザリングなど）の Chrome で開く | 接続でき、出演者名（メモ）が表示され、音声が届く |
| 受信ページを再読み込みする・一度切断して再接続する | 再接続できる |
| トンネルを再起動したあと、古い URL を開く | 接続できない。新しい URL では接続できる |

## 4. RTSP E2E 計測（V11）

| 手順 | 期待する結果 |
|---|---|
| PR #55 より前の版（v8.2.0 など）で、OBS の配信を開始して RTSP 計測を3回行い、計測値を記録する | — |
| 同じ配信先・同じ回線で、現在の版で RTSP 計測を3回行う | 計測が成立する。計測値の差が、許容すると決めた範囲（例: 数十 ms 以内）に収まる |
| RTSP URL を手動指定にして `http://example.com/` を入力し、計測を始める | 計測が始まらない |

差が大きい場合は、映像を受信しない入力制限（`-allowed_media_types audio`）を見直す。

## 5. 子プロセスの終了（V12）

| 手順 | 期待する結果 |
|---|---|
| トンネルを起動中に、タスクマネージャーで `obs64.exe` を強制終了する | `cloudflared.exe` も消える |
| RTSP 計測中に、タスクマネージャーで `obs64.exe` を強制終了する | `ffmpeg.exe` も消える |
| 上の確認の前に OBS のログを見る | `is not in the kill-on-close job` の警告が出ていない |

## 6. 運用（V13〜V15）

| 手順 | 期待する結果 |
|---|---|
| 出演者20人相当（複数の端末・タブ）で接続し、WS 計測と RTSP 計測を行う | 全員に音声が届き、チャンネル別のディレイが適用される。上限による誤った切断が無い |
| 設定を保存して OBS を再起動する・OBS のシーンコレクションを書き出して読み込み直す | 値が失われない |
| LAN 直接配信を使っていた以前の版の設定を読み込む | URL 共有はトンネルの URL だけになり、エラーにならない |
| 各タブを行き来し、設定を変更したあと OBS のログを見る | 表示が崩れない。ログにチャンネルコードや受信本文が出ていない |
