# release-tag スキル

バージョン番号の更新、CHANGELOG 追記、コミット、タグ作成、プッシュまでを一括で行う。
プレリリースでは CHANGELOG を書かず、版の更新とタグだけを行う（「プレリリース」の節）。

## 引数

`$ARGUMENTS` の解釈:

| 入力例 | 動作 |
|--------|------|
| `2.1.0` / `v2.1.0` | そのバージョン番号で正式リリース（`v` は除去） |
| `major` / `minor` / `patch` | 現在バージョンに対して指定レベルをバンプして正式リリース |
| `2.1.0-rc.1` / `v2.1.0-rc.1` | そのバージョン番号でプレリリース |
| `rc` / `major rc` / `minor rc` / `patch rc` | プレリリース。版は「バージョン自動判定ルール」または指定レベルで決め、N は既存タグから決める |
| （空） | コミット内容から自動判定して正式リリース（下記ルール） |

### バージョン形式の制約

- 正式リリースは `X.Y.Z`（各要素は非負整数）、プレリリースは `X.Y.Z-rc.N`（N は 1 以上の整数）だけを受け付ける。
- それ以外のサフィックス（例: `2.0.0-beta.3`, `1.0.0-alpha`, `1.0.0-rc`）はエラーとして中断する。
- bump レベル指定や自動判定では常にこの形式が生成されるため、制約に抵触しない。

## バージョン自動判定ルール

引数が空（または `rc` だけ）の場合、以下の手順で次バージョンを決定する:

1. `CMakeLists.txt` から現在のバージョン `CURRENT` を読み取る。
2. `v{CURRENT}` の正式タグがなく、`v{CURRENT}-rc.*` のタグだけがある場合は、プレリリース中の版とみなし、次バージョンを `CURRENT` とする（正式リリースなら rc を経た版の確定、`rc` なら次の rc）。以降の手順は行わない。
3. `git log` で前回の正式タグ（`-` を含まないタグ。`v{CURRENT}`）から HEAD までのコミットメッセージと diff の概要を確認する。
4. 以下の基準で bump レベルを判定する:

| 判定 | 条件（いずれかに該当） | 例 |
|------|----------------------|-----|
| **major** | 後方互換性のない変更、プロトコル/API の破壊的変更、設定ファイル形式の非互換変更 | WebSocket メッセージ形式の変更 |
| **minor** | 新機能の追加、UI の新規画面・項目、新しい設定項目 | Opus 対応追加、新しい計測モード |
| **patch** | バグ修正、パフォーマンス改善、リファクタリング、ドキュメント修正、ビルド修正 | クラッシュ修正、CSS 調整 |

5. 判定結果とバージョン番号をユーザに提示し、確認を取る。ユーザが別のレベルやバージョンを指定したらそちらに従う。

major を上げると、保存設定の互換判定（major 一致）により、旧版で保存したフィルターは警告専用モードになり、作り直しが必要になる。major を提示するときはこの影響も伝える。

## ビルド失敗後の再リリース検出

正式リリースのときだけ行う。

### 検出条件

コミット収集後、以下の **両方** が成立する場合は「前バージョンのビルドが失敗した再リリース」と判定する:

1. 前回タグ (`v{CURRENT}`) から HEAD までのコミットが **すべて** 以下のいずれかのみ
   - `fix(ci):` / `fix(build):` / `chore(ci):` / `chore(build):` / `Release v*` コミット
2. CHANGELOG.md に `## v{CURRENT}` セクションが存在する

### 検出時の処理

1. ユーザに「前バージョン `v{CURRENT}` のビルドが失敗した再リリースと判定しました。`v{CURRENT}` の CHANGELOG 内容を新バージョンに統合しますか？」と確認を取る。
2. 同意を得た場合:
   - 新バージョンの CHANGELOG セクションに `v{CURRENT}` の内容を取り込む（統合後の全体をユーザに提示して確認）
   - **`v{CURRENT}` セクションを CHANGELOG から削除する**（内容が新バージョンに移動したため重複を排除）
3. 拒否された場合: 通常の手順で新バージョンのセクションのみ追記する。

## 手順（正式リリース）

### 1. 事前確認

- 現在のブランチが `main` であることを確認する。`main` でなければユーザに警告して確認を取る。
- ワーキングツリーがクリーンであることを確認する（未コミットの変更がないこと）。汚れていたら中断する。
- 同じタグ (`v{VERSION}`) が既に存在しないことを確認する。

### 2. 変更内容の把握とバージョン決定

- `git log` で前回の正式タグから HEAD までのコミットを確認する（タグがない場合は全履歴）。rc タグは区切りに使わない。
- 引数がなければ「バージョン自動判定ルール」に従って次バージョンを決定する。
- 「ビルド失敗後の再リリース検出」を実施する。
- 変更内容をユーザ目線で要約し、**決定したバージョン番号と CHANGELOG に書く内容** をユーザに提示して確認を取る。

### 3. ファイル更新

以下のファイルのバージョン番号を更新する（rc で既に `X.Y.Z` になっていれば CHANGELOG だけ）:

| ファイル | 更新箇所 |
|---------|---------|
| `CMakeLists.txt` | `project(obs-delay-stream VERSION X.Y.Z)` |
| `README.md` | 1行目のタイトル `# obs-delay-stream  vX.Y.Z` |
| `README-en.md` | 1行目のタイトル `# obs-delay-stream  vX.Y.Z` |
| `CHANGELOG.md` | 先頭に新バージョンのセクションを追加（日本語、既存フォーマットに合わせる）。再リリース時は前バージョンのセクションを削除する。 |

**CHANGELOG のフォーマット:**
```markdown
## vX.Y.Z — YYYY-MM-DD

### セクション名（変更内容に応じて選択）

- **機能名** — 説明
```

セクション名は変更内容に応じて `新機能`、`改善`、`修正`、`ビルド・配布`、`破壊的変更` などから適切に選ぶ。

### 4. コミット

```
git add CMakeLists.txt README.md README-en.md CHANGELOG.md
git commit -m "Release vX.Y.Z"
```

### 5. タグ作成

```
git tag vX.Y.Z
```

### 6. プッシュ

コミットとタグを両方プッシュする:

```
git push origin HEAD
git push origin vX.Y.Z
```

## プレリリース

CI は `-` を含むタグを Pre-release の下書きリリースにし、CHANGELOG の抽出を飛ばす。プラグインの UI・受信ページ・ログには、CI がタグから渡す suffix 付きの版（例: `9.0.0-rc.1`）が出る。CI はタグの `X.Y.Z` と `CMakeLists.txt` の版が食い違うとビルドを止めるため、タグより先に版を上げる。

1. 事前確認は正式リリースと同じ（`main`・クリーン・同じタグがない）。
2. 版 `X.Y.Z` を決める（引数、または「バージョン自動判定ルール」）。N は既存の `vX.Y.Z-rc.*` タグの最大値 + 1（なければ 1）。決めた `vX.Y.Z-rc.N` をユーザに提示して確認を取る。
3. `CMakeLists.txt` の版が `X.Y.Z` でなければ、`CMakeLists.txt`・`README.md`・`README-en.md` の版を `X.Y.Z` に上げてコミットする。CHANGELOG は更新しない（正式リリースのときにまとめて書く）。

   ```
   git add CMakeLists.txt README.md README-en.md
   git commit -m "Prepare vX.Y.Z"
   ```

4. タグを作成してプッシュする。

   ```
   git tag vX.Y.Z-rc.N
   git push origin HEAD
   git push origin vX.Y.Z-rc.N
   ```

5. CI が作る下書きリリースの本文は空になる。公開前に GitHub 上で本文を書き、公開するようユーザに伝える。

## 注意事項

- バージョン番号の正式な定義は `CMakeLists.txt` の `project(VERSION)` のみ。C++ コードや HTML はビルド時にマクロ / configure_file で自動展開されるため手動更新不要。プレリリースの suffix は CI が `-DODS_VERSION_SUFFIX` で渡す。
- `build.bat` のバナー表示バージョンは更新対象外。
- ファイルヘッダコメント (`.hpp` / `.cpp`) にバージョン番号は書かない。
